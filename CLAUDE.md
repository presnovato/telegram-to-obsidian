# CLAUDE.md — TikTok / X → Obsidian

**Status:** MVP реализован, 287 тестов зелёные (было 105: +63 форварды, +11 лок/сторож, +47 ревью-1, +62 ревью-2 F1–F14 и O4, +4 фиксы приёмки R1–R3; плюс 11 node-тестов плагина). Режимы захвата (vault/chat/both) реализованы, но **на живом боте не прогнаны** — чек-лист приёмки во внутреннем `docs/merge-plan.md` §5 (эти документы не публикуются). Источник X добавлен и проверен сквозным прогоном на живых постах (одиночное фото и цитата) во временный vault: скачивание, заметка, дедуп, приём подменённого домена fixupx.com. Не проверено: TikTok-ветка на живой ссылке (нужен токен + реальный пост — за заказчиком), пост X с видео и с каруселью. Форварды Telegram (§ ниже) реализованы по внутреннему `docs/tz-telegram-forwards.md` (не публикуется), на живом боте не прогнаны — приёмка в §11 того же файла.

**Stack:** Python 3.13, aiogram 3 (long polling), yt-dlp (библиотека), python-dotenv. Без БД, без Railway — полностью локальный бот на ПК заказчика (Windows), пишет прямо в файловую систему vault (путь берётся из `VAULT_ROOT` в `.env`).

**Источники:** TikTok (yt-dlp + tikwm) и X/Twitter (зеркала эмбедов). Общая папка медиа, разные папки заметок. Плюс пересланные Telegram-сообщения (форварды) — НЕ URL-источник: файлы забираются через Bot API, а TikTok/X-ссылки внутри отдаются существующему пайплайну как связанные посты; правило «новый источник = новый downloader» на Telegram не распространяется.

**Режимы захвата:** `vault` (только заметка) / `chat` (только в чат, vault не трогаем) / `both` (историческое поведение). Переключение — `/mode`, выбор переживает перезапуск (`state.json`). Разовое переопределение — токен `!chat` / `!vault` / `!both` в сообщении со ссылкой. Слой доставки в чат перенесён из отдельного проекта `twitter-to-telegram`, который этим слиянием закрывается.

## Entry Points
- `python -m tiktok_obsidian [--parent-pid PID]` — запуск бота: вручную из VS Code (без флага) или из Obsidian-плагина (с флагом для сторожа родителя).
- `obsidian-launcher/` — плагин-супервизор `t2o-launcher`: стартует бота при открытии хранилища, гасит при закрытии. Сборка: `npm install && npm run build && npm run deploy` (vault через `T2O_VAULT_DIR` или `deploy.local.json`, в репо путь не хардкодится).
- Команды в чате: `/mode [vault|chat|both]`, `/status`, `/update_ytdlp`, `/errors`.
- `python -m pytest` — тесты по чистым функциям core.

## Key Files
- `config.py` — секреты из .env, пути vault (MEDIA_DIR, NOTES_DIR, NOTES_DIR_TWITTER, NOTES_DIR_TELEGRAM), константы. `notes_dir_for(source)` — папка заметок по источнику. `validate()` при старте. Форварды: `TG_ALBUM_WAIT_S` / `TG_COMMENT_WAIT_S` / `TG_MAX_LINKED_POSTS`.
- `core/` — **чистый домен, без импортов telegram/yt-dlp**: `urls.py` (`extract_post_url` — TikTok и X, при двух ссылках берёт первую по тексту; `extract_post_urls` — все ссылки по порядку, для форвардов), `naming.py` (имена файлов, очистка под Windows), `note.py` (шаблон заметки + `related`/`warnings`/`plain_files` для Telegram; дефолт байтово тот же), `fs.py` (атомарная запись, дедуп по ФС), `models.py` (PostMeta, Source), `twitter.py` (regex ссылки X + чистый разбор JSON зеркал), `telegram.py` (форварды: origin → post_id/author/url, entities → Markdown в единицах UTF-16, сбор ссылок incl. text_link, link-only).
- `downloader/` — маршрутизация по источникам: `__init__.py` диспетчеризует (probe — по виду ссылки, download — по `meta.source`) и заворачивает сбои любого движка в общий `DownloadError`.
  - `twitter.py` — X через зеркала эмбедов, каскад `api.fxtwitter.com` → `api.vxtwitter.com`. Ключей и аккаунта X не требуют, медиа на публичном CDN twimg. Сеть на urllib — новых зависимостей проект не тянет. Микрокэш на 8 записей, чтобы probe и download не ходили в сеть дважды.
  - `ytdlp.py` — TikTok. Качаем во временную папку **на том же диске, что и vault** (иначе `os.replace` даёт WinError 17 при переносе C:→D:) → переименовываем в `{video_id}[_NN].ext`.
  - **Видео → yt-dlp** в основном. Если yt-dlp отвечает «No video formats found», сначала проверяем фото-данные; когда изображений нет, используем TikWM-видео в порядке hdplay → play → wmplay. Вариант wmplay помечается как watermarked. Лимит UPLOAD_LIMIT_MB применяется к chat-загрузкам, но не к сохранению в vault.
  - **Фото/карусели → web-данные yt-dlp** (`_images_from_ytdlp_web`, `imagePost.images[]`): приватный метод экстрактора, при обновлении yt-dlp может измениться. Фолбэк — tikwm.com API (`_tikwm_fetch`). TikWM может временно отвечать 403; при видеофолбэке варианты пробуются по очереди.
  - **Короткие ссылки разворачиваем сами** (`_resolve_short_url`, HEAD, микрокэш на 32 записи). yt-dlp идёт по редиректу внутри себя, получает путь `/photo/` и падает с «Unsupported URL» — переписать ссылку там уже некому. `_prepare_url` = резолв + `normalize_for_ytdlp`, применяется во всех трёх точках входа в yt-dlp (probe, download, web-извлечение картинок). Сбой резолва не фатален: отдаём исходную ссылку.
  - **probe**: yt-dlp основной, при провале фолбэк `_tikwm_meta`. yt-dlp-логгер в probe заглушён (`_QuietLogger`), т.к. провал ожидаемо ловится фолбэком.
  - `core.urls.normalize_for_ytdlp` переписывает `/photo/` → `/video/` для yt-dlp (чистая функция, сети не знает — резолв живёт в `downloader/`).
- `core/mode.py` — чистый слой режима: `CaptureMode`, `parse_mode`, `strip_mode_override` (токен `!chat` в тексте).
- `mode_store.py` — персистентность режима в `state.json` (не в `.env`: он ручной, переписывать его из кода = однажды потерять чужую строку). Битый файл откатывает на `CAPTURE_MODE`, а не роняет старт.
- `delivery.py` — доставка в чат. `deliver_urls` (X: прямые ссылки, фолбэк качает только недоставленное) и `deliver_files` (TikTok и vault-режим: готовые файлы). Чанки медиа-групп 2–10 без хвоста-одиночки; заливки идут с `UPLOAD_TIMEOUT_S` через `Bot.__call__`, URL — по дефолту.
- `downloader/net.py` — единый `open_url` с `MEDIA_PROXY` (только http/https; socks мимо). yt-dlp получает прокси своей опцией.
- `service.py` — оркестрация probe → дедуп → download → заметка. Плюс `plan_chat`/`download_to` для chat-режима (без дедупа и без заметки).
- `telegram_capture.py` — оркестрация форвардов (§8 спеки): дедуп по `tg_`-ID → файлы Bot API (лимит 20 МБ) → OCR 2+ картинок → связанные посты через `service` → заметка последней. Общий `process_lock` с capture. Колбэки `download`/`process_link` — для тестов без бота.
- `main.py` — argparse (`--parent-pid`), `InstanceLock` до `validate()`, коды выхода для плагина: 0 чисто / 4 конфиг (`ConfigError`, не рестартить) / 2 краш (рестартить) / 3 уже запущен (не рестартить). Код 1 reserved (taskkill/смерть на импорте = краш для плагина). Числовые env парсятся хелпером в `ConfigError` с именем переменной. Без флага сторожа нет. `_poll_forever` отправляет Telegram/aiohttp/OS/python-socks/aiohttp-socks proxy connection errors в backoff; сообщение показывает замаскированный `TELEGRAM_PROXY` и подсказку запустить прокси-клиент или очистить переменную. `TelegramUnauthorizedError` преобразуется в `ConfigError` (exit 4). Backoff ждёт через shutdown-событие, поэтому watchdog прерывает ожидание.
- `instance_lock.py` — single-instance: эксклюзивный `msvcrt.locking` на байте со смещением 1<<30 (лок мандатный: байт 0 сделал бы PID нечитаемым; `locking` лочит от текущей позиции — нужен явный seek). ОС снимает лок при смерти процесса.
- `watchdog.py` — сторож родителя раз в 5 с (`OpenProcess` + `WaitForSingleObject`, проверка за функцией для тестов). `stop_polling()` у aiogram — корутина; вне polling кидает `RuntimeError`, в стартовой гонке молча возвращается — сторож ставит shutdown-событие и долбит stop каждую секунду + хард-фолбэк `os._exit(0)` через 30 с. Дренаж висящих форвардов (`on_shutdown`) — пока сессия жива, до stop.
- `handlers/` — тонкий telegram-слой: `commands.py`, `forward.py` (`F.forward_origin`, склейка альбомов, спаривание комментариев, link-only-делегация в capture-поток, `resolve_comment`, `drain_pending` + `_INFLIGHT` для graceful shutdown), `burst.py` (буфер альбомов/комментариев с инжектируемыми часами, `flush_all`), `capture.py` (catch-all, регистрируется последним; текст без ссылки держит как комментарий к форварду).
- `middleware.py` — owner-only по `ALLOWED_USER_ID`.

## Правила
- `core/` и `downloader/core` не импортируют telegram. Всё тестируемое без бота — в core.
- **Один токен — один процесс.** Второй экземпляр исключён локом `bot.lock` (код 3), а не договорённостью. PID в лок-файле — только для людей, правда — сам лок.
- **Живость процесса — только через `OpenProcess`/`WaitForSingleObject`.** `os.kill(pid, 0)` на Windows не пробует, а **убивает** цель (`TerminateProcess`). Никогда не использовать для проверок.
- Дедуп — только по файловой системе (`{video_id}.*` в Медиафайлах). Никакой БД в MVP.
- **Пост X без медиа — валидный пост, а не сбой.** Текстовый твит сохраняется заметкой (`media_files=[]`); каскад зеркал в `downloader/twitter.py` держит ответ без медиа как запасной и предпочитает ему ответ с медиа (второе зеркало могло увидеть медиа в цитате). Такой пост не оставляет файлов в Медиафайлах, поэтому дедуп для него сверяется с заметками — сигнал `PostMeta.has_media`, якорь `post_id` во frontmatter (имя заметки строится из описания и ID не содержит).
- **ID постов X префиксуются `x_`.** ID X и aweme-ID TikTok — числа одного диапазона, а дедуп и имена файлов завязаны на `video_id`. Без префикса они однажды столкнутся.
- Новый источник = новый модуль в `downloader/` + ветка в диспетчере + `Source` в моделях. Ни `service.py`, ни `handlers/` трогать не нужно. Telegram-форварды — исключение: это не URL-источник, у него нет модуля в `downloader/`, файлы идут через Bot API (`telegram_capture.py` + `handlers/forward.py`).
- Порядок роутеров: команды → forward → capture (catch-all последним).
- Все имена файлов через `naming.sanitize_filename` (запрещённые Windows-символы), запись через `fs.atomic_write_text` (tmp → replace).
- Хэштеги остаются в тексте описания; в именах заметок `#^[]` вычищаются (`#adhd` → `adhd`), иначе ломаются вики-ссылки «Связанных постов»; раздел «Впечатления» — только если заказчик прислал комментарий.
- yt-dlp обновляется вручную (`/update_ytdlp`), авто-обновлений нет. Для X он не используется: требует cookies залогиненного браузера и ломается вслед за изменениями X.
- **HTML-превью fixupx.com не парсить** — у того же проекта есть JSON-эндпоинт, он отдаёт все медиа с сохранением порядка, а `og:video` — только одно видео и разваливается на карусели.
- Расхождения зеркал X (проверено на живых данных, лечится в `core/twitter.py`):
  - vx кладёт в media превью ссылочной карточки (`pbs.twimg.com/card_img/`), fx — нет. Фильтруем, иначе пост-ссылка приезжает картинкой чужого сайта.
  - fx на цитате без своих медиа отдаёт пустой `media`; берём медиа из `tweet.quote`, автор и текст остаются от цитирующего поста.
- Карусель для X = больше одной **картинки**. Пара видео каруселью не считается — иначе OCR поедет по видео.
- Альбом в чат собирается пофайлово (`InputMediaPhoto`/`InputMediaVideo` по расширению): пост X может смешивать фото и видео.
- **В chat-режиме дедуп не применяется** — он основан на наличии файлов в vault, а vault не пишется. Повторная отправка в чат считается осознанной.
- **Размер медиа заранее не проверяем.** Зеркала его не сообщают достоверно (у vx `size` — размеры кадра), поэтому единственный честный сигнал «не влезло» — отказ Telegram. Отказ переводит доставку в режим «скачать и залить файлом».
- **GIF не кладётся в `media_group`** — Telegram запрещает animation в альбоме, GIF уходит отдельным `answer_animation`. Вид медиа известен только для X (`TweetMedia.kind`); после скачивания это просто mp4.
- **httpx в зависимости не тянуть.** Доставка качает на urllib в `asyncio.to_thread`, как и `downloader/`.
- Chat-режим для TikTok всё равно скачивает: прямых ссылок на медиа `probe` не даёт. Временная папка — **на диске vault** (`dir=MEDIA_DIR.parent`), иначе WinError 17.

## Deploy
Деплоя нет — локальный запуск. Разовая настройка: `.env` (токен, user id) + опционально `Meta/Медиафайлы/*.mp4` в `.gitignore` самого vault (вариант A из ТЗ). Бот .gitignore vault не трогает.
